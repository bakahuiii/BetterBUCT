# 安全政策

BetterBUCT 处理教务凭据、北化在线凭据和校园数据。本政策说明如何报告安全问题以及我们如何处理这些问题。

---

## 🔐 安全承诺

我们致力于保护用户的隐私和数据安全：

- 🔒 使用 Android Keystore 加密存储凭据
- 🚫 不上传用户数据到开发者服务器
- 🌐 严格限制网络访问到校园域名
- 🛡️ 代码开源，接受社区审查
- ⚡ 快速响应和修复安全问题

---

## 🚨 报告安全问题

### 私密报告渠道

**请勿在公开 Issue、Pull Request、讨论区或任何公开渠道报告安全漏洞。**

使用以下私密渠道报告：

#### 方式一：GitHub 私密安全通告（推荐）

1. 访问 [提交私密安全报告](https://github.com/bakahuiii/BetterBUCT/security/advisories/new)
2. 填写漏洞详情（见下方模板）
3. 提交后只有项目维护者可见

#### 方式二：GitHub 私信

如果无法使用安全通告：

1. 访问项目维护者的 GitHub 个人页面
2. 通过私信联系
3. 说明是安全问题并请求私密讨论

**重要**：不要把敏感内容改发到公开 Issue！

### 报告内容模板

```markdown
## 漏洞概述
简要描述安全问题的性质和影响。

## 影响范围
- 受影响的版本：v0.2.x
- 受影响的组件：（如：凭据存储、网络层、导出功能等）
- 影响用户：（如：所有用户、特定配置的用户等）

## 复现步骤
1. 第一步
2. 第二步
3. ...

## 实际影响
- [ ] 凭据泄露
- [ ] 数据泄露
- [ ] 权限绕过
- [ ] 代码执行
- [ ] 其他：___________

## 利用条件
需要什么前置条件才能触发此漏洞？

## 建议修复方案（可选）
如果有修复建议，请提供。

## 附件
- 不包含真实个人数据的日志
- 请求/响应样例（脱敏后）
- 概念验证代码（如果安全）
```

### 报告要求

✅ **应该包含**：
- 清晰的问题描述
- 复现步骤
- 影响范围评估
- 脱敏后的日志或样例

❌ **不应包含**：
- 真实的学号、密码
- 真实的 Cookie、Token
- 完整的个人数据
- 签名密钥
- 可直接利用的 exploit 代码（在修复前）

## 🎯 安全问题范围

### 在范围内的问题

我们接受以下类型的安全报告：

#### 1. 凭据泄露
- 密码在日志、导出文件或调试界面中泄露
- 凭据通过不安全渠道传输
- Keystore 实现不当导致的凭据暴露

#### 2. 数据泄露
- 用户数据未经授权访问
- 数据导出包含不应导出的敏感信息
- 应用间数据共享不当

#### 3. 网络安全
- 绕过校园域名白名单
- 绕过重定向校验
- 中间人攻击风险
- 明文流量泄露敏感信息

#### 4. 权限问题
- 越权访问其他用户数据
- 权限提升
- 沙箱逃逸

#### 5. 注入攻击
- 代码注入
- 命令注入
- WebView 相关的 XSS（如果影响到凭据或数据安全）

#### 6. 加密问题
- 弱加密算法
- 不当的密钥管理
- 不安全的随机数生成

#### 7. 构建和发布
- 发布包中暴露签名材料
- 源代码中硬编码的密钥
- 依赖项的已知漏洞

### 不在范围内的问题

以下问题**不作为安全漏洞处理**（可以提交普通 Issue）：

#### 1. 校园服务本身的问题
- 教务系统的账号策略
- 北化在线的安全措施
- 校园网络的配置问题

#### 2. 使用不当
- 用户主动分享账号密码
- 用户在不安全环境中使用
- 用户安装恶意改版

#### 3. 已知限制
- 文档中已明确说明的限制
- 浏览器预览的安全级别低于原生

#### 4. 低风险问题
- 应用崩溃（不导致数据泄露）
- 界面显示错误
- 性能问题

**注意**：如果不确定是否属于安全问题，可以先私密报告，我们会评估并引导到合适的渠道。

## 🔄 处理流程

### 1. 确认（1-3 个工作日）

- 维护者确认收到报告
- 初步评估是否属于安全问题
- 决定是否需要更多信息

### 2. 评估（3-7 个工作日）

- 复现漏洞
- 评估影响范围和严重程度
- 确定修复方案

### 3. 修复（取决于严重程度）

- **严重**（凭据泄露、数据泄露）：1-7 天
- **高危**（权限绕过、网络安全）：7-14 天
- **中危**（加密问题、注入风险）：14-30 天
- **低危**（其他）：30-60 天或随下一版本

### 4. 发布

- 发布修复版本
- 在 Release Notes 中说明修复的安全问题（不披露细节）
- 更新安全通告状态

### 5. 披露（修复后）

修复发布后：
- 与报告者协商披露时间（通常 30-90 天）
- 公开安全通告
- 致谢报告者（如果报告者同意）

---

## ⏱️ 合理等待时间

我们请求报告者：

- 在修复发布前不公开披露
- 给维护者合理的修复时间
- 不通过漏洞获取他人数据或破坏服务

如果修复时间超出预期：
- 我们会及时通报进展
- 可协商临时缓解措施
- 可协商披露时间

---

## 🏅 安全致谢

我们感谢负责任地报告安全问题的研究者。根据漏洞的严重程度和报告质量，我们会：

1. **公开致谢**（如果报告者同意）
   - 在 Release Notes 中致谢
   - 在安全通告中署名
   - 在 README 中列出（对于重大漏洞）

2. **报告反馈**
   - 及时的进展更新
   - 修复方案的技术讨论
   - 修复验证的邀请

**注意**：BetterBUCT 是开源项目，目前**不提供**漏洞赏金。

## 🛡️ 贡献者的安全职责

如果你为 BetterBUCT 贡献代码，请遵守以下安全准则：

### 代码安全

- ✅ 使用参数化查询，避免注入
- ✅ 验证和清理用户输入
- ✅ 使用安全的加密算法
- ✅ 正确处理错误，不泄露敏感信息
- ✅ 遵循最小权限原则

### 凭据处理

- ✅ 只通过 `TheiaVaultPlugin` 读写凭据
- ✅ 不在日志中输出密码、Cookie
- ✅ 导出功能不包含凭据
- ✅ 测试使用假数据，不提交真实凭据

### 网络安全

- ✅ 保持域名白名单限制
- ✅ 验证 HTTPS 证书
- ✅ 校验重定向目标
- ✅ 不绕过安全措施

### 依赖管理

- ✅ 使用有明确版本的依赖
- ✅ 定期检查依赖漏洞
- ✅ 避免可疑的依赖包
- ✅ 不使用 `eval()` 执行动态代码

### 提交前检查

在提交 PR 前，确认：

- [ ] 代码不包含硬编码的密钥或凭据
- [ ] 日志和调试代码已移除
- [ ] 测试数据已脱敏
- [ ] `.gitignore` 中的敏感文件未被提交
- [ ] 新增的网络请求在白名单内

详见 [贡献指南](CONTRIBUTING.md)。

## 📋 安全检查清单

### 发布前检查

发布新版本前，维护者应检查：

- [ ] 所有依赖为已知安全版本
- [ ] `keystore.properties` 和 `*.keystore` 不在仓库中
- [ ] 源代码中无硬编码密钥
- [ ] APK 签名正确
- [ ] ProGuard 规则保护关键类
- [ ] 网络安全配置正确
- [ ] 权限声明最小化
- [ ] Release Notes 不包含敏感信息

### 代码审查检查

审查 PR 时，检查：

- [ ] 无明显的安全漏洞
- [ ] 凭据处理符合规范
- [ ] 网络请求在白名单内
- [ ] 输入验证充分
- [ ] 错误处理不泄露信息
- [ ] 无测试凭据或敏感数据
